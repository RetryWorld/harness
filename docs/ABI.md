# ABI stability policy

`include/harness/harness_kernel.h` and `include/harness/harness_critic.h` are
the contract (build brief §6). Two things are diffed in CI on every PR:

1. **The headers themselves**, against the base branch. Any textual change is
   flagged for review — most are fine (a comment, a new non-ABI-affecting
   declaration), but reordering or removing a struct field, changing a
   function signature, or renumbering a status/decision/band enum value is
   not, ever.
2. **The exported symbol table**, `nm -D --defined-only` on the built
   `libharness_kernel.so`, filtered to `hk_`/`hkc_` symbols and committed at
   `edge/abi/symbols.txt`. A symbol appearing, disappearing, or changing is
   flagged the same way. This catches what a header diff can miss — e.g. a
   function removed from the header but still exported, or vice versa.

Either diff failing blocks the PR **unless**:

- `HK_ABI_VERSION` (or `HKC_ABI_VERSION` for the critic ABI) is bumped in the
  same PR, and
- a row is added to the changelog below describing the change.

`HK_ABI_VERSION` is not tied to the kernel's release version (`PROJECT_VERSION`
in `CMakeLists.txt`) — a patch release must not force every consumer to
recompile. It moves only when the ABI itself moves.

A C11 translation unit (`tests/abi/c_consumer.c`) that includes the header and
calls every function is built and run in CI regardless of what the C++
implementation does, so the header stays valid C even if nothing else in this
repo is.

## Bootstrapping `edge/abi/symbols.txt`

`nm -D` is a Linux-only tool (ELF `.dynsym`, not a Mach-O `.dylib` concept), so
this file can only be regenerated by CI running on `ubuntu-latest`, not by
hand from a macOS checkout. If `edge/abi/symbols.txt` is absent, the CI job
generates it, uploads it as a workflow artifact, and passes without
enforcing a diff — download that artifact and commit it as
`edge/abi/symbols.txt` to establish the baseline for the next PR.
